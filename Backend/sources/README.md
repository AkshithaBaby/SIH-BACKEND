# Predictive ESS Screening Backend

Backend for the Burn-In latent-defect hackathon problem: dynamic (lot-relative)
outlier detection + time-series drift prediction, with QA-facing explainability.

## Setup

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Open `http://localhost:8000/docs` for interactive Swagger UI (auto-generated by FastAPI).

## Test with synthetic data first

Real ESS datasets are hard to come by, so `generate_synthetic_data.py` produces
`synthetic_readings.json` with three part types baked in:
- **Normal parts (~85%)**: gentle linear drift.
- **Latent defect type 1 (~8%)**: already a lot-relative outlier by 24h, but
  still under the datasheet max → this is exactly the case Module A is built to catch.
- **Latent defect type 2 (~7%)**: looks nominal through 24h, then accelerates
  sharply → this is exactly the case Module B's forecasting is built to catch.

```bash
python generate_synthetic_data.py
```

Then feed `synthetic_readings.json` into `/drift/train` (to fit the correction
model on historical/known-168h data) and `/screen` (to get verdicts on new
components) via the Swagger UI or curl.

## Architecture

```
app/
  schemas.py           Pydantic request/response models
  module_a_outlier.py  Dynamic outlier detection (robust z-score per lot)
  module_b_drift.py    Baseline linear extrapolation + RF correction + safety-slope check
  pipeline.py           Merges A + B into a single QA verdict per component
  main.py               FastAPI routes
generate_synthetic_data.py   Synthetic data for testing before real data exists
```

## Module A — Dynamic Outlier Detection

**Why not just mean/std?** A handful of true defective parts inflate the mean
and standard deviation, which masks the very outliers you're trying to catch.
Instead we use per-lot, per-parameter **median and MAD (Median Absolute
Deviation)** — robust up to a 50% breakdown point — and the **Modified Z-score**
(Iglewicz & Hoaglin):

```
M_i = 0.6745 * (x_i - median) / MAD      (threshold: |M_i| > 3.5)
```

The absolute datasheet limit is kept as a **hard, non-negotiable safety net** —
dynamic detection only ever adds sensitivity on top of it, never relaxes it.
This matters because the rubric explicitly penalizes false negatives.

Every flag returns the median, MAD, z-score, and a plain-English explanation —
this is what satisfies the "can it justify itself to a QA inspector" requirement.

## Module B — Drift Predictor

Two-layer design, kept deliberately interpretable:

1. **Physics-informed linear baseline** (fully explainable):
   `rate = (V24 - V0) / 24`, then `forecast_168h = V24 + rate * 144`.
2. **RandomForest correction** trained on historical parts with known 168h
   values, predicting the *residual* between the true value and the linear
   baseline (not the raw value) — this keeps the ML model's job small and
   bounded, and its `feature_importances_` are surfaced via `/drift/train`
   so the correction itself is inspectable rather than a total black box.
   If fewer than 10 labeled historical rows are available, the system
   **falls back to baseline-only** automatically rather than overfitting.

**Safety slope**: `(datasheet_max - V24) / 144` — the max sustainable rate
of change from 24h onward that still lands at the limit by 168h. A
`safety_margin` parameter (default 0.85) tightens this for conservatism.

## Combining Module A + B (`/screen`)

A component is **REJECT**ed if *either* module independently flags it —
they are not averaged/voted, since averaging could dilute one strong
signal and let a real defect slip through.

## Tuning knobs to highlight to judges

- `z_score_threshold` (Module A sensitivity)
- `safety_margin` (Module B conservatism — evaluation-recall tradeoff)
- Swap `RandomForestRegressor` for `GradientBoostingRegressor` or a
  simple `Ridge` regression if you want to trade a bit of MAE for even
  more explainability (linear coefficients instead of tree importances).

## Known limitation / next step

On the synthetic data, the RF correction cut baseline MAE from ~29.7 to
~7.0, but recall on the fast-accelerating "type 2" defect class was still
moderate at the default margin — worth tuning `safety_margin` down (more
conservative) and/or adding `value_96h` as a feature if your real dataset
includes a mid-point reading, since a third timepoint disambiguates
accelerating drift much better than two points alone.
